| `EV:PRELOAD` serial event → `event_history` → `action` string | Firmware-originated event data flowing into a host-side decay-windowed lookup. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-04 | Tampering | 9 new no-op/delegating gcode command stubs | low | accept | 7 are bare `pass`-equivalent no-ops (`cmd_MMU_NOOP`); the other 2 delegate only to the pre-existing, already-accepted `_FLARE_SYNC_TOOLHEAD` macro with no new parameter surface (no `RESET` passed) — no new state-changing capability is introduced beyond what `_FLARE_SYNC_TOOLHEAD` already does today via other call sites. |
| T-14-05 | Denial of Service | `_recent_event_seen` scanning `event_history` under `event_history_lock` on every `klipper_syncer` wake | low | accept | `event_history` is capped at 100 entries (`scripts/flare_daemon.py:98-106`) and the scan early-`break`s once entries age past `within_s` (2.0s), so worst case is a short, bounded, infrequent lock hold — no unbounded growth or blocking risk. |
| T-14-06 | Spoofing | A crafted `mmu_machine.happy_hare_version` value misleading Fluidd/Mainsail into taking an unintended UI code path | low | accept | The value is a static, developer-chosen string (never derived from untrusted input); worst case is a cosmetic UI-branch mismatch, not a security issue. Documented verification attempt in Task 2 reduces (does not eliminate) this risk. |

</threat_model>
